OAuth2, JWT, and other ways to cure Insomnia

Mar 10 2026 · 12 min read · Shubham

OHHHHHH MYYYYYY GOOOOOOOOOOOD, what a week I just lived. Yeah so basically I just built a full auth system from scratch email sign-in, Google, Apple, JWT, access tokens, refresh tokens, public/private keys, scoped permissions, the works and I have thoughts. A lot of them. Chaotic ones. And I need to write them down before they evaporate.

TLDR: USE FIREBASE.

Okay but first what even is auth?

Let me just make it clear that:

Authentication is who are you. Are you really Shubham? Prove it.
Authorization is what are you allowed to do. Okay Shubham, you're real, but can you access this document?

These two things sound similar but they're architecturally very different. Authentication happens once at login. Authorization happens on every single request. The whole system I built sits on this distinction. Keep it in your head.

The OAuth2 dance "Sign in with Google"

Okay. Sign in with Google. Looks simple from the outside button, consent screen, logged in. Under the hood? Merlin's beard, there are steps.

Here's the actual flow. Claude will draw it, because he helped me when I was alone.

Yeah. Ten steps. You know what, the first time I read about this I was like nah man, why so many steps, why can't Google just... give me the user? The answer comes down to one thing: the code exchange in step ⑥ happens server-side, not in the browser. The browser never sees Google's tokens. This matters because the browser is public anyone can look at it. Your backend is private. So the sensitive Google access token lives only there.

The Callback URL

It wasted my entire afternoon.

The callback URL (step ⑤) is the URL Google redirects to after the user approves. You register this URL in Google Cloud Console. Google will only redirect to URLs you've pre-registered if there's any mismatch (different port, different path, different scheme), it just rejects it. Fine. Reasonable.

Here's what got me. In Google Cloud Console, OAuth credentials are typed. You create a credential for a specific platform: Web application, Android. I had created an iOS credential. iOS credentials use a custom URI scheme like com.myapp:/oauth2redirect. That's a deep link into a mobile app.

So when I tested on PC browser: user clicks login, gets consent screen, approves... and then nothing. Blank. No redirect. No error. Just a void. I'm sitting there like you sure about that, Google? I did everything right! The user consented! Where did the redirect go?!

It went to com.myapp:/oauth2redirect. In a PC browser. Which has no app to handle that URI scheme. So it just... dropped it silently. No error. Just gone. Into the void.

The fix was to create a Web application credential with http://localhost:8000/auth/google/callback registered as the redirect URI. Different credential type, different client ID entirely. The moment I switched instant redirect, everything worked.

And the saviour during all this debugging: OAuth Playground (developers.google.com/oauthplayground). It's Google's own tool for testing OAuth flows. It has its own pre-registered redirect URI so it always works regardless of your Console setup. Absolute lifesaver. If you're building any Google OAuth thing, keep this tab open.

Public and Private Keys

Hmm Hmm; it's important so it's here. I'll write more on the actual math sometime later. For now just look at the diagram.

The intuition: think of it like a wax seal on a letter. The private key is your unique stamp only you have it, only you can press it. The public key is how anyone can recognise your seal as genuine. They can look at it and say "yes, Shubham sealed this." But they can't forge a new seal with the same impression. Recognition ≠ forgery.

How are they derived? The private key is just a very large random number. The public key is computed from it using elliptic curve multiplication a mathematical operation that is easy to compute in one direction (private → public) and effectively impossible to reverse (public → private). You can share the public key with the entire internet and nobody learns anything useful about your private key.

And here's why this is actually sick for our system: once I give the public key to any microservice in my backend, that service can verify JWTs forever without ever calling my auth server again. Zero network hops. Stateless verification. That's the payoff.

The JWT What's Actually Inside

Okay real talk step ⑧ in the flow I showed earlier raised a question I had myself: why issue your own JWT? Google already gave you a token, why not use that?

Because Google's token is Google's business. It has Google's expiry, Google's format, Google's scopes. And for your own API, you want to put your own claims in the token things like user ID in your database, user roles, subscription status, whatever your system cares about. Google doesn't know any of that.

A JWT is just three base64-encoded chunks joined by dots: header.payload.signature. 

// Header
{
  "alg": "RS256",
  "typ": "JWT"
}

// Payload (your claims readable by anyone!)
{
  "sub": "user_id_in_your_db",
  "email": "shubham@example.com",
  "roles": ["user"],
  "iat": 1743724800,
  "exp": 1743728400
}

// Signature: sign(base64(header) + "." + base64(payload), private_key)
// If someone tampers with payload, signature check fails → rejected

Important: the payload is not encrypted, just encoded. Anyone can read it. So don't put secrets in there.

"The signature only guarantees it wasn't tampered with, not that it's hidden. Ah really, caught me off guard when I first understood this."

Access Token + Refresh Token Why Two?

You sure about needing two tokens? Yes. Here's why.

The reason for two tokens is a security trade-off. If the access token gets stolen somehow (network log, browser cache, whatever), it expires in 15 minutes. Damage contained. The refresh token is long-lived but it's only ever sent to one specific endpoint (/auth/refresh), stored carefully, and the client silently swaps it when access tokens expire user never notices.

The get_user_auth Pattern

Ok ok ok this is my favourite part to talk about because it's the bit that made the whole system feel clean. Every API endpoint in my backend depends on a function I called get_user_auth. It does one thing: verify the JWT from the request header and return the user. If it fails expired token, tampered payload, missing header it raises a 401 immediately. The endpoint never runs. 

async def get_user_auth(token: str = Depends(oauth2_scheme)) -> User:
    try:
        payload = jwt.decode(token, PUBLIC_KEY, algorithms=["RS256"])
        user_id = payload.get("sub")
        if not user_id:
            raise credentials_exception
    except JWTError:
        raise credentials_exception

    user = await db.get_user(user_id)
    if not user:
        raise credentials_exception
    return user


# Every endpoint that needs auth:
@router.get("/documents/{doc_id}")
async def get_document(doc_id: str, user: User = Depends(get_user_auth)):
    # user is guaranteed valid here. No auth logic in here.
    return await db.get_doc(doc_id, owner=user.id)

simple right? yeah because its simple, there is nothing to smile about.

Scoped Permissions "I Only Need Docs"

Last thing, and this one is conceptually elegant once you see it.

In my system, certain flows require specific Google permissions not just identity, but actual capability. Like if a feature needs to read the user's Google Docs, I need the https://www.googleapis.com/auth/drive.readonly scope. The user needs to grant that specifically.

So the flow is: frontend launches Google OAuth with the exact scopes that particular feature needs. User sees a consent screen that says specifically "This app wants to read your Google Drive." User approves. Google gives back tokens with exactly those capabilities. Backend stores them and uses them only for that feature. 

SCOPES = {
    "identity":    ["openid", "email", "profile"],
    "docs_read":   ["openid", "email", "https://www.googleapis.com/auth/drive.readonly"],
    "docs_write":  ["openid", "email", "https://www.googleapis.com/auth/drive"],
}

def get_google_auth_url(scope_key: str, state: str) -> str:
    scopes = SCOPES[scope_key]
    return oauth.google.authorization_url(
        scope=scopes,
        redirect_uri=CALLBACK_URL,
        state=state,
        access_type="offline",  # get refresh token
    )

The reason you do it this way ask for only what you need is both security practice and user trust. Nobody's granting "full Google Drive access" to an app they just found.
