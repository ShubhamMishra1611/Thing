The Forbidden Jutsu of Python Configuration

Apr 15 2025 · 10 min read · Shubham

In the ancient chronicles of coding, legends tell of a time when raw, unbridled energy surged from the primordial language of C - a force revered as "The Primordial." Recognizing its formidable power, a great sage transformed this potent energy into what we now call CPython. Fueled by the might of C, CPython allows you to channel this energy effortlessly with a simple import.

While studying CPython Configurations and PyConfig, I stumbled upon how this hidden energy is controlled. It's all about managing CPython's configuration state - arranging variables, setting flags, and shaping the runtime environment to your will. Almost like tuning the flow of an ancient force.

Key Elements of Execution

Before executing any CPython code, it requires:

  • A module to execute
  • A state to store runtime information (variables, etc.)
  • A configuration that dictates runtime behavior

1. A Module to Execute

A module is just a piece of Python code - either a single script (.py file), a package, or built-in Python functionality. When you run:

python script.py

or

python -m http.server 8080

The Python interpreter loads the module, prepares it for execution by setting up required variables, and executes the module's code. Every Python program is treated as a module when executed, including the __main__ module for standalone scripts.

Python uses __main__ to distinguish between scripts run directly (standalone) and modules being imported.

2. A State to Hold Information

Python manages the storage of variables, functions, and objects while executing code through an execution state. This execution state stores variables (x = 10), function definitions (def greet(): ...), class objects, and imported modules.

Where is this stored? Python maintains this execution state in a global state container inside CPython, which includes:

  • Global Interpreter State (GIS) - stores core Python execution settings: memory management, object references, garbage collection, current thread state, loaded modules, and configuration settings like debug mode and optimization flags.
  • Local Execution Contexts - stores variables specific to a function or block of code.
  • Garbage Collector State - keeps track of memory allocations.

3. A Runtime Configuration

Before executing code, Python needs to configure settings like memory management, encoding settings (UTF-8, locale), and debugging options (verbose or isolated mode). This configuration process is managed using PEP 587, which introduced key components: PyPreConfig for pre-initialization settings, and PyConfig for runtime settings.

Understanding Python's Configuration Settings

PEP 587 introduced a standardized way to configure the CPython interpreter.

Pre-Initialization Configuration (PyPreConfig)

The pre-initialization configuration runs before Python starts and is mainly used for:

  • Setting up memory allocators
  • Defining locale and encoding (UTF-8 settings)
  • Choosing isolation mode

Key settings include:

  • isolated - enable isolated mode. When enabled, sys.path contains neither the script's directory nor the user's site-packages directory.
  • legacy_windows_fs_encoding - (Windows only) disable UTF-8 mode and set filesystem encoding to mbcs.
  • use_environment - if greater than zero, use environment variables.
  • utf8_mode - if nonzero, enable UTF-8 mode.
  • dev_mode - if nonzero, enable development mode with extra warnings and debug hooks.

Example: Setting Pre-Initialization Configuration in C

#include <Python.h>

int main() {
    PyPreConfig preconfig;
    PyPreConfig_InitPythonConfig(&preconfig);

    PyStatus status = Py_PreInitialize(&preconfig);
    if (!handle_py_status(status)) {
        return 0;
    }

    preconfig.utf8_mode = 0;  // Disable UTF-8 mode

    Py_Initialize();
    PyRun_SimpleString("print('Hello from Python with preconfig!')");
    Py_Finalize();
    return 0;
}

We initialize PyPreConfig to configure settings, enable UTF-8, then start Python with Py_Initialize().

Here handle_py_status is a function for checking PyStatus - a structured error handling system in the Python C API:

int handle_py_status(PyStatus status) {
    if (PyStatus_Exception(status)) {
        if (status.err_msg != NULL) {
            fprintf(stderr, "Error: %s\n", status.err_msg);
        } else {
            fprintf(stderr, "Unknown Python error occurred\n");
        }
        return 0; // Failed
    }
    return 1; // Success
}

Runtime Configuration (PyConfig)

Once Python starts, PyConfig manages runtime values like runtime flags (debug, optimized), execution mode (script, stdin, or module), extended options (via -X), and environment variables (e.g., PYTHONHOME).

#include <Python.h>

int main() {
    PyConfig config;
    PyConfig_InitIsolatedConfig(&config);

    config.isolated = 1;
    config.use_environment = 0;
    config.user_site_directory = 0;

    PyStatus status = Py_InitializeFromConfig(&config);
    if (!handle_py_status(status)) {
        PyConfig_Clear(&config);
        return 0;
    }

    PyRun_SimpleString(
        "print('Python running with custom runtime settings!')"
    );

    Py_Finalize();
    return 0;
}

Compile-Time Configuration

Some settings must be decided at compile-time when CPython is built from source. Examples:

  • sys.maxsize (determined by platform architecture)
  • Debug mode (./configure --with-pydebug)
  • Optional modules (enabling/disabling optimizations)

You can check these with:

python -m sysconfig

If you install Python from different sources (official, Homebrew, Anaconda), these settings may vary.

The Isolation Experiment

Let's isolate libraries from Python. A simple way is to use a virtual environment or the -I flag. But we can do the same by setting PyPreConfig and PyConfig directly.

Here's the test script we want to run inside our isolated environment:

import sys
print(f'sys.flags.isolated = {sys.flags.isolated}')
print(f'sys.flags.no_user_site = {sys.flags.no_user_site}')
print(f'"site" in sys.modules = {"site" in sys.modules}')

imports_to_test = ['numpy', 'os', 'sys', 'builtins', 'site']
for pkg in imports_to_test:
    try:
        __import__(pkg)
        print(f'Can import {pkg}: YES')
    except ImportError:
        print(f'Can import {pkg}: NO')

And here's the C program that runs it in full isolation:

#include <Python.h>
#include <stdio.h>
#include <stdlib.h>

int test_full_isolation(void) {
    // Pre-initialize with isolated configuration
    PyPreConfig preconfig;
    PyPreConfig_InitIsolatedConfig(&preconfig);
    preconfig.isolated = 1;
    preconfig.use_environment = 0;

    PyStatus status = Py_PreInitialize(&preconfig);
    if (!handle_py_status(status)) return 0;

    // Use isolated config with explicit site_import=0
    PyConfig config;
    PyConfig_InitIsolatedConfig(&config);
    config.isolated = 1;
    config.use_environment = 0;
    config.user_site_directory = 0;
    config.site_import = 0;

    status = Py_InitializeFromConfig(&config);
    if (!handle_py_status(status)) {
        PyConfig_Clear(&config);
        return 0;
    }

    PyRun_SimpleString(
        "import sys\n"
        "print(f'sys.flags.isolated = {sys.flags.isolated}')\n"
        "print(f'\"site\" in sys.modules = "
            "{\"site\" in sys.modules}')\n"
        "\n"
        "for pkg in ['numpy', 'os', 'sys', 'builtins', 'site']:\n"
        "    try:\n"
        "        __import__(pkg)\n"
        "        print(f'Can import {pkg}: YES')\n"
        "    except ImportError:\n"
        "        print(f'Can import {pkg}: NO')\n"
    );

    PyConfig_Clear(&config);
    Py_Finalize();
    return 1;
}

The result: numpy cannot be imported in isolation. Standard library modules (os, sys, builtins) still work because they're built into CPython itself.

Ways to Execute Python Code

CPython allows Python code execution through multiple approaches:

  • Command line - python -c "print('Hola Amigo')"
  • Module execution - python -m unittest test_script.py
  • Piping input - echo "print('hehe')" | python (no -c flag needed)
  • REPL - just type python and enter the Read-Eval-Print Loop
  • Embedding in C - using Python.h and the CPython C API
  • Script file - python script.py

Note on compiling C with embedded Python:

gcc embed_python.c -o embed_python.exe \
    -I"<PathToPython>/Python312/include" \
    -L"<PathToPython>/Python312/libs" \
    -lpython312

From Input to Executable Code

Before Python executes any code, it must convert input into a module. CPython follows a multi-step process:

  1. Read input (file, string, stdin, module, or bytecode)
  2. Pass it to the parser (converts it into an AST)
  3. Compile it into bytecode
  4. Execute the module within the __main__ namespace

A. Input String from Command Line (-c flag)

python -c "print(2 ** 2)"

The command is passed to pymain_run_command() inside Modules/main.c, converted into a Python bytes object using PyUnicode_FromWideChar(), then passed to PyRun_SimpleStringFlags() which implicitly creates a __main__ entry point and calls PyRun_StringFlags() to generate an AST from the string.

B. Input with a Local Module (-m flag)

python -m unittest

Python finds the module inside sys.path, sets __name__ = "__main__" to indicate standalone execution, and executes the module inside Lib/runpy.py. Executing python -m <module> and python -m runpy <module> are equivalent.

C. Input from a Python Script (.py file)

python script.py

The file is opened and read into memory. PyRun_SimpleFileExFlags() parses and compiles it, creating a __main__ module. The script is then executed in the global namespace. This same function also handles .pyc files and stdin when you pipe input.

D. Input from Precompiled Bytecode (.pyc files)

python compiled_script.pyc

Instead of parsing source code, CPython directly loads the precompiled bytecode. PyRun_SimpleFileExFlags() detects the .pyc file and calls run_pyc_file(), which deserializes the file into a code object and executes it.
